## 1. What Tim found

Ulla Hees came out of the run with rows on **Saturday 2026-08-22 and Sunday
2026-08-23** — days she does not work — carrying **no punches at all**. Entry and
Exit empty, Late and Early `—`, DOC reading `Form Submitted` without saying which
form.

**It was not a parsing accident.** The engine already gated every date on the
employee's `work_days`. The bug was one level in, in what the gate *did*:

| On a day off | Was | Now |
|---|---|---|
| Punches, no form | row dropped silently | **YELLOW row with the real punches** |
| Form, no punches | **YELLOW row created** | no row |
| Neither | no row | no row |

It asked *"is there a form?"* when it should have asked *"are there punches?"*.
`permissionCoversDate` is a plain inclusive string range with no work-day filter,
so a permission running Friday→Monday matched the Saturday and Sunday between it
and manufactured a row on each.

Ten such rows existed in `Q2-Aug-2026`, across four employees — Elizabeth
Mootoo, Juan Fonseca, Tanya Bedoya, Ulla Hees. **Eight had already been resolved
by Tim**, which is the second time in three days he has spent effort on rows
that should never have existed.

### Where the DOC column now points

`Form Submitted` was written from three branches spanning three different boards.
It no longer appears anywhere in the engine:

| Board | DOC value |
|---|---|
| Permissions & Requests | `Permission Form` |
| GAF Attendance | `Attendance Form` |
| Time Adjustments | `Time Adjustment Form` |

`hasTft` was one boolean OR-ing two boards; it is now split into
`tftAdjustment` / `tftPermission` so the DOC can name the board that actually
drove the row to YELLOW.

Also: a **Floating Holiday** used to land as generic `Permiso Remunerado` /
`Paid`, indistinguishable from any other paid permission. It now carries
`Floating Holiday / B-Day Off` — a value seeded in `pay_impacts` since day one
that the engine had never once emitted — and goes YELLOW, as do unpaid
permissions. Ordinary PTO still auto-resolves GREEN.

## 4. Two corrections I made to my own work

**W4 and W5 broke in Round 1 — they had passed before.** Both used the off-day
punch idiom (punch on a Saturday, assert zero rows) to prove Saturday was a day
off. Under the new rule that punch legitimately produces a row, so the idiom
stopped expressing the intent. They now assert the row is the off-day YELLOW one
by its `auto_notes`, and W4 gained a control proving a scheduled Monday does not
carry that note. I should have caught them in Round 0.

**W9's control used a request type that does not exist.** I wrote
`'Time Off / Permission'`, which matches nothing in `PAID_PERM_TYPES`
(`classificationEngine.ts:546`), so it fell through to the no-data absence branch
and returned `Ausencia Injustificada`. Changed to `'Compensatory Day'`. W9's
actual assertion — zero Saturday and Sunday rows — passed first time.

**Worth checking, NOT a claim:** the config description for
`monday_col_requests_request_type` lists `Time Off / Permission` as a real option
on that board, and it is not in `PAID_PERM_TYPES` either. Whether such requests
reach the engine under a different string, or genuinely fall through to RED,
needs checking against live data before anyone calls it a bug.

## 6. The operating lesson from today

**Only ever have one builder tab open.** The two-tab workflow is fine only while
the export tab stays on a `/dev/…` URL. Loading `/edit/…` in it opens a second
editor session, the two diverge, and the round's save is blocked behind an
`Overwrite their changes / Reload from their version` dialog that nothing in the
loop looks at.

It cost Round 2 an attempt, and **none of the existing checks caught it**: UI
Bakery reported both files edited and the imports confirmed, Export produced a
genuinely new zip, and `sync-export` still said `0, 0, 0`. The "did a new zip
appear?" rule does not help, because the export really did run — it just
exported unchanged files.

Choose **Reload from their version**; it discards only what a committed prompt
can regenerate. Now in `LESSONS.md`, with a note to check for that dialog before
exporting.
