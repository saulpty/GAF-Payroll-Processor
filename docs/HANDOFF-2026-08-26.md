## 1. The headline: deleted rows were being counted almost everywhere

`payroll_entries` rows are soft-deleted, never removed. `loadHrkSummary` and
`loadPayrollMaster` filtered `deleted_at IS NULL`. **Eight other read paths did
not**, so the same period reported different figures depending on which screen
you opened.

Measured on `Q2-Aug-2026` before the fix: the Summary Dashboard read **308.2**
discount hours while HRK Summary read **182.2**. The 126.0-hour gap was exactly
the 18 phantom off-day rows migration `1781900200` deleted on 08-25.

**It was proved from two screens of the app itself**, no database access needed:
Period Log listed Cemiriamiz Iglesias 2026-08-11 as deleted by
`migration-1781900200-weekend-offday-cleanup`, while Action Required showed that
same row as live work awaiting resolution.

### What it cost Tim

While the review was running, the Committed-to-GREEN list was found to contain
**all 18 phantom rows**, marked *Permiso Remunerado / Paid / Day Off*, timestamped
14:26–14:27 — Euclides 5, Michael 5, Cemiriamiz 4, Edwin 4, exactly the
migration's own breakdown. He had spent the morning carefully resolving rows that
had been deleted the day before, because the queue kept showing them to him.

**Fixed.** Committed to GREEN fell from 74 to exactly 56, predicted before
measuring. Dashboard and HRK Summary now both read 182.2h and agree. Period Log
still lists all 20 deleted rows and they remain restorable.

### Guard tests — the suite went 96 → 100

`tests/lessonGuards.test.ts` enforces four traps `LESSONS.md` says have bitten
repeatedly. L1 (params-wrapper) and L2 (`{{params}}` in a quoted string) are
strict. **L3 (timezone) and L4 (ProcessPayroll's Monday ids) are ratchets**: they

fixed one is left stale in the list, so the numbers can only go down.

## 4. Things that are true but unsatisfying — read before assuming

- **The `v_attendance_daily` fix has no visible effect.** All 18 deleted rows are
  off-day rows, and that view has filtered on each employee's `work_days` since
  `1781900100` landed the day before, so they were already excluded. The change
  guards a case that does not exist yet: a deleted row on a day someone actually
  works. It could not be distinguished from "the view did not update" through the
  UI alone, because UI Bakery exposes no SQL runner.
- **Migration `1781900300`'s header comment is wrong.** It was copied verbatim
  from `1781900100` and still describes the `work_days` change, including a
  Rollback line naming the wrong file. The filename and the commit message are
  accurate. Left alone rather than re-prompting against verified SQL.
- **`attendanceStats.ts:245` still uses `toISOString`.** Deliberate, with a NOTE
  above it. That module must stay import-free or `node --test` cannot resolve it.
  The proper fix is to pass today's date in from the caller.
- **A date-only string like `2026-08-26` still parses as UTC midnight** in
  `parseWallClock`'s fallback. It is not timezone-bearing by the new test. A
  Teramind row with a date and no time is degenerate data either way.

## 5. Two operating lessons, both now in `LESSONS.md`

**The clipboard mangled every prompt.** `Get-Content -Raw | Set-Clipboard` reads
as ANSI in PowerShell 5.1, so prompts 01–04 reached UI Bakery with
`LATE â€" UNREPORTED` in them. It never broke a change — only decorative
punctuation was hit — but that is luck. The length tells you: 4249 characters via
the default encoding, 4215 as real UTF-8.

**Coordinate clicks drift mid-round.** One click meant for the AI textarea landed
2px below it and typed nothing; another meant for *Export* navigated to a
different app entirely.

**What works, every time:** base64 the prompt file, decode it in the page, set the
textarea through React's native value setter, dispatch `input`, then click
`button.submit-message` found in the DOM. Same for Export — find the `.menu-item`
whose text is `Export`. Verify `.value.length` against the file's character count
before submitting. Every round after switching to this landed first time.

## 8. Accessibility — what was done and what to check

Two rounds, both after the main sweep.

**Focus is visible everywhere.** Styling existed on 13 of 136 interactive
elements. One unlayered rule in `index.css` now draws a 2px navy outline on
`:focus-visible` for every button, link, input, select, textarea and anything
with a `tabindex`. Verified with a real Tab: `solid / 2px / rgb(27, 58, 107) /
2px`.

**This took two attempts, and the reason is worth knowing.** The rule was first
written inside `@layer base` using `:where()`. Afterwards `outline-offset` came
through but `outline-style` computed as `none` — it was matching and losing.
**In CSS any unlayered rule beats any layered rule regardless of specificity**,
and UI Bakery's theme is unlayered; `:where()` also contributes zero specificity.
Rewritten unlayered with explicit longhands marked `!important`, which is the
justified use of it: an accessibility floor a vendor reset would otherwise remove
silently.

**Keyboard row selection.** Action Required's employee name was a click handler
on a bare `<span>` — the page's primary action was mouse-only. It now has
`role="button"`, `tabIndex={0}`, `aria-pressed`, and an Enter/Space handler that
preserves shift-range-select. Verified: Enter → "1 row selected", Space → "0".

**Nine icon buttons have names.** The app had exactly one `aria-label`, on a
decorative icon. The Attendance panel's close button and the seven
save/cancel/edit/delete buttons in Rules & Config are now named.

**Two things to eyeball when you're next at the app**, both method limitations
rather than known faults:

- Clicking a **select or text input** with the mouse now shows the navy outline.
  That is spec-correct — browsers keep the indicator on keyboard-operable
  controls — but it is a *visible* change, not the invisible one first intended.
  Buttons should stay silent on mouse click; every test click landed on a select,
  so that half is unverified.
- The keyboard handler was verified by dispatching a `KeyboardEvent`, which React
  handles identically to a real key. A physical Return did not reach the element,
  because key events do not route into the builder's nested iframe from this
  harness. Thirty seconds of manual tabbing would close it out.
