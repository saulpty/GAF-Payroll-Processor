Written before the data was seen, so worth recording that the data moved them.

1. **`state` is a region, not employment status.** Vitasya 16, GA 8, IN 5, GA
   West 4, GA East 4, PA 3, AZ 2, OH 1, one blank. The spec's example row said

   contracts; the board carries one, already ended. She became the `ended`
   example rather than a live countdown.
3. **Five edge cases have zero live instances** — no board row, blank contract
   end, null roster start, board-vs-roster start mismatch, two live board rows
   for one person. All handled defensively, all proved by unit test rather than
   on screen. The "N not on the Onboarding board" notice renders nothing today.

Also corrected, in the other direction: an acceptance line claimed the 30d
toggle would leave exactly one row. It leaves **7 of 44**, because the toggle
catches milestones as well as contract ends. The behaviour was right; the
criterion was wrong.

### Deleting the duplicate Euclides: BLOCKED, and it should stay blocked

Saul: *"the duplicate false javier delete him."*

**It cannot be deleted, and the database is right to refuse.**

| | id 47 (inactive) | id 49 (active) |
|---|---|---|
| email | `javierqvistgaard@hotmail.com` | `javier.g@passiontocarehc.com` |
| payroll_entries (live) | **10** | 30 |
| name_aliases | 0 | 1 |
| monday_contracts | **1** | 0 |
| pto_employees | 1 | 1 |
| schedule_id | 1 (Mon–Fri) | 10 (weekend) |

`payroll_entries.employee_id` is `NOT NULL REFERENCES employees(id)` with no
`ON DELETE` clause, so Postgres refuses the delete while those **10 rows in
`Q2-Jul-2026`** exist. That period is already paid; removing or moving those
rows changes historical totals, which is the same question `BACKLOG.md` #13 is
still waiting on.

And a delete would not fix the symptom anyway: the three `monday_*` mirrors are
`ON DELETE SET NULL`, so deleting 47 would blank his contract row's
`employee_id` and leave it **unmatched** — worse than today.

**A repoint is also not durable.** `syncContracts` re-resolves `employee_id` by
name on every sync, and both records carry the same `display_name`, so the next
sync would undo it.

**The real options, for Saul to choose:**

1. **Leave it.** 47 is already inactive and its note already reads
   `[DUPLICATE - personal email, deactivated]`. Cost: he shows as
   *Not on Onboarding board* on Contracts, and his contract end 2027-01-21 is
   attached to a record nobody queries.
2. **Merge properly** — move the 10 `Q2-Jul-2026` payroll rows and the
   `pto_employees` row from 47 to 49, repoint `monday_contracts`, then delete 47.
   This touches an already-paid payroll period, so it needs Saul's explicit
   go-ahead and a check for date collisions against 49's own rows first.
3. **Make name resolution prefer the active record**, so the sync stops picking
   47. A code change to `mondaySync.ts`, and the only option that fixes the
   class of problem rather than this instance.

Nothing was deleted. See
